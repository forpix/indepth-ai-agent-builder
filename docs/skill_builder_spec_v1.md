# Skill Builder 配置项精确设计 v1.0

> 鼎捷面试 Demo 的 C 位屏（Skill Builder）的配置项级别精确设计。
> 用途：作为 Claude Code 生成 UI 的精确输入，避免 Claude Code 自由发挥。

---

## 0. 布局总览

Skill Builder 整屏分三栏，左 / 中 / 右：

```
┌─────────────┬──────────────────────────┬──────────────┐
│             │                          │              │
│  左：模块导航  │     中：当前模块配置区        │   右：预览区  │
│             │                          │              │
│  - 元信息    │   [当前选中模块的配置表单]   │  - Skill 卡片 │
│  - 触发      │                          │  - 模拟运行   │
│  - 筛选规则   │   ⚠️ 冲突预警在此处展示       │  - 复用统计   │
│  - 动作      │                          │              │
│  - 自动化边界 │                          │              │
│  - 模型路由   │                          │              │
│  - 知识检索   │                          │              │
│             │                          │              │
│  ──────────  │                          │              │
│             │                          │              │
│  [Low Code]  │                          │              │
│  [Code View] │                          │              │
│             │                          │              │
└─────────────┴──────────────────────────┴──────────────┘
```

**顶部全局区**：

- Skill 名称（可编辑）
- 版本号（v1.0.0 自动递增）
- 保存 / 发布 / 另存为模板 / 切换 Code View 四个按钮

**左侧固定**，**中间随选中模块切换**，**右侧实时根据中间配置更新**。

## 1. 全局 UI 设计原则

| 原则 | 实现方式 |
|------|---------|
| **配置项之间的依赖关系要可见** | 被依赖的配置项变化时，相关配置项自动 disable / 高亮提示 |
| **冲突预警必须实时** | 中间配置区底部有一个固定的"冲突检查"小卡片，任何冲突出现立刻显示 |
| **每个配置项都有 tooltip** | 鼠标悬停展示"这个配置项是做什么的 + 为什么这么设计" |
| **业务术语用鼎捷化语言** | "任务卡"代替"消息推送"，"知识封装"代替"知识库"，"智能体"代替"Agent" |
| **视觉风格** | B 端工具风，蓝灰主色，参考鼎捷雅典娜官网调色 |

## 2. 模块一：元信息（Skill Metadata）

| 配置项 | UI 形态 | 默认值 | 是否必填 | 依赖关系 |
|--------|--------|--------|---------|---------|
| Skill 名称 | 单行输入框 | "制造业采购交期跟催 Skill" | ✓ | 无 |
| 适用行业 | Multi-select | ["装备制造", "汽车零部件"] | ✓ | 影响后续筛选规则的预设选项 |
| 业务领域标签 | Tag 输入框 | ["采购协同", "供应商管理"] | - | 用于模板市场检索 |
| Skill 描述 | 多行文本 | （预填一段 50 字描述）| ✓ | 无 |
| 适用 ISV 角色 | Multi-select | ["业务顾问", "开发者"] | ✓ | 决定 Code View 是否可见 |
| 版本号 | 自动只读 | "v1.0.0" | 自动 | 每次发布递增 |
| 模板来源 | 下拉框 | "从零开始" / "基于官方模板" / "Fork 自其他 ISV" | - | 选模板时自动预填后续配置 |

**面试讲点**：

> 元信息这一块看起来简单，但有一个产品判断——**"适用 ISV 角色" 决定了 Code View 是否可见**。如果这个 Skill 标记为"仅业务顾问使用"，开发者可以查看 Code View 但不能编辑；如果标记为"开发者可参与"，Code View 全开放。这是低代码与高代码并存的产品形态：**权限不是按用户，是按 Skill 配置的可见度决定**。

## 3. 模块二：触发方式

| 配置项 | UI 形态 | 默认值 | 是否必填 | 依赖关系 |
|--------|--------|--------|---------|---------|
| 定时触发 | Toggle + Cron 表达式输入 | 开启 / "0 8 * * *"（每天 8 点） | - | 无 |
| 手动触发 | Toggle | 开启 | - | 无 |
| 自然语言触发 | Toggle | 开启 | - | 启用后会被 Agent Console 调用 |
| 事件触发 | Toggle + 事件源 Multi-select | 关闭 / ["MRP 计划变动", "工单插单"] | - | 启用时显示事件源选择 |

**冲突预警示例**：

- 如果四个触发方式都关闭，底部冲突卡片显示：⚠️ "至少需要启用一种触发方式，否则 Skill 不会被执行"

**面试讲点**：

> 这一块的产品判断是 **四种触发方式并存，但有优先级**。事件触发的优先级最高（业务变动需要立刻响应），定时触发兜底（即使其他都没触发也保证每天检查一次），手动触发用于例外场景。我没有把它做成"四选一"的单选，因为真实 ISV 场景里这四种触发往往同时存在。

## 4. 模块三：筛选规则 ⭐ 核心模块

这个模块是 Skill Builder 的最厚一块，也是面试官最容易追问的地方。

### 4.1 筛选规则的 UI 形态

不用拖拽画布，用**分组的配置卡片**：

```
┌────────────────────────────────────┐
│ 📋 时间筛选                          │
│ ┌────────────────────────────────┐│
│ │ 到货前 N 天   [Slider: 1─14] 7天││
│ │ 排除已完结订单 [Toggle: 开]      ││
│ └────────────────────────────────┘│
├────────────────────────────────────┤
│ 📋 供应商筛选                        │
│ ┌────────────────────────────────┐│
│ │ 供应商回复状态  [Multi: 未回复] ││
│ │ 供应商等级     [Multi: A,B]    ││
│ │ 历史延期率阈值  [Slider: 0─50%] ││
│ └────────────────────────────────┘│
├────────────────────────────────────┤
│ 📋 物料属性筛选                      │
│ ┌────────────────────────────────┐│
│ │ 是否关键件     [三态: 是/否/不限]││
│ │ 是否单一来源    [三态: 是/否/不限]││
│ │ 是否有替代料   [三态: 是/否/不限]││
│ └────────────────────────────────┘│
├────────────────────────────────────┤
│ 📋 影响范围筛选                      │
│ ┌────────────────────────────────┐│
│ │ 影响在制工单    [Toggle]        ││
│ │ 影响 MRP 计划   [Toggle]        ││
│ │ 影响客户订单    [Toggle]        ││
│ │ 客户重要性下限   [下拉: 普通/KA] ││
│ └────────────────────────────────┘│
└────────────────────────────────────┘
```

### 4.2 详细配置项表

| 分组 | 配置项 | UI 形态 | 默认值 | 依赖关系 |
|------|--------|--------|--------|---------|
| 时间筛选 | 到货前 N 天 | Slider 1-14 | 7 | 无 |
| 时间筛选 | 排除已完结订单 | Toggle | 开 | 无 |
| 供应商筛选 | 回复状态 | Multi-select [未回复 / 已回复延期 / 已回复确认] | [未回复] | 无 |
| 供应商筛选 | 供应商等级 | Multi-select [A / B / C] | [A, B] | 无 |
| 供应商筛选 | 历史延期率阈值 | Slider 0-100% | 30% | 仅当筛选模式为"主动跟催"时启用 |
| 物料属性 | 是否关键件 | 三态选择（是 / 否 / 不限） | 不限 | 选"是"时自动联动到"自动化边界 → 必须人工" |
| 物料属性 | 是否单一来源 | 三态选择 | 不限 | 同上联动 |
| 物料属性 | 是否有替代料 | 三态选择 | 不限 | 无 |
| 影响范围 | 影响在制工单 | Toggle | 关 | 启用时显示工单 ID 列表 |
| 影响范围 | 影响 MRP 计划 | Toggle | 关 | 启用时需要授权访问 MRP 模块 |
| 影响范围 | 影响客户订单 | Toggle | 关 | 启用时显示客户订单 ID |
| 影响范围 | 客户重要性下限 | 下拉 [全部 / KA 客户 / 仅战略客户] | 全部 | 仅在"影响客户订单"启用时可见 |

### 4.3 配置项依赖关系图

```
   [是否关键件 = 是]──────┐
   [是否单一来源 = 是]────┼──→ 自动联动"自动化边界 → 必须人工复核"
                          │
   [影响在制工单 = 开]────┘
                          
   [筛选模式]──→ 影响"历史延期率阈值"是否可用
                          
   [影响客户订单 = 开]──→ 解锁"客户重要性下限"
```

**面试讲点**：

> 筛选规则这一块我做了一个产品判断：**物料属性的"三态选择"（是 / 否 / 不限）**，而不是二态 Toggle。
>
> 真实场景里 ISV 会说"我只想跟催关键件"——这是"是"；也会说"我只想跟催非关键件"——这是"否"；还会说"我不在乎是不是关键件"——这是"不限"。如果做成二态 Toggle，"否"和"不限"会混淆，导致 ISV 在配置时心智负担很大。三态是处理"包含 / 排除 / 不约束"这种业务语义的正解。
>
> 另一个判断是 **配置项之间的隐式联动要可见**。比如"是否关键件 = 是"会自动联动到"自动化边界 → 必须人工复核"——这是规则优先级里"安全 > 业务 > 效率"的具体落点。在 UI 上我会用一条虚线把两个配置项连起来，让 ISV 一眼看到隐式联动。

## 5. 模块四：动作配置

### 5.1 配置项表

| 动作类别 | 动作名称 | UI 形态 | 默认值 | 依赖关系 |
|---------|---------|--------|--------|---------|
| 通知类 | 发送供应商跟催 | Toggle + 通知渠道 Multi-select | 开 / [任务卡, 企业微信] | 必须有通知渠道才能启用 |
| 标记类 | 标记加急 | Toggle | 关 | 启用时联动"必须人工确认" |
| 升级类 | 发起二次跟催 | Toggle + 间隔 Slider（小时） | 关 / 24h | 启用时联动"跟催次数上限" |
| 升级类 | 创建异常任务 | Toggle + 升级人选择 | 开 / "采购主管" | 必须配置升级接收人 |

### 5.2 ⭐ "调用其他 Skill" 这一项是埋钩子

这一项是多智能体协同的产品入口——可以在面试时讲：

> 我专门留了"调用其他 Skill"这一项，是因为鼎捷 Commander 2.0 + MACP 协议是 2025 年的旗舰故事。这一项让采购跟催 Skill 能调用"齐套预警 Skill"或"供应商风险评估 Skill"——是多智能体协同的产品入口。具体的 MACP 协议实现交给架构师，但**产品形态上"Skill 之间可以相互调用"的可能性必须留出来**。

### 5.3 动作配置的 UI 形态

每个动作是一个折叠卡片，开启 Toggle 时展开配置：

```
│ ▶ 发送供应商跟催              [ON] │
│   通知渠道: ☑任务卡 ☑企业微信 ☐邮件 │
│   话术模板: [选择...]              │
│   附加附件: ☐采购单 PDF             │
└─────────────────────────────────────┘
```

## 6. 模块五：自动化边界 ⭐ 平台 PM 思考的核心展示位

### 6.1 三层固定优先级（v1.1 已确认的设计）

```
┌─────────────────────────────────────┐
│ 🔒 安全层（不可关闭）                │
│   - 影响在制工单 → 必须人工          │
│   - 关键件 → 必须人工                │
│   - 单一来源 → 必须人工              │
│   - 财务合规事项 → 必须人工          │
├─────────────────────────────────────┤
│ 📊 业务层（可配置）                  │
│   - 延期 ≤ N 天 [Slider 0-7] 自动同意│
│   - 供应商等级 A → 自动同意          │
│   - 客户重要性 ≥ KA → 必须人工       │
├─────────────────────────────────────┤
│ ⚡ 效率层（默认开启）                 │
│   - 跟催次数上限 [Slider 1-5] 3 次   │
│   - 自动同意范围限制 [Slider] ¥10000 │
└─────────────────────────────────────┘
```

### 6.2 配置项表

| 层级 | 配置项 | UI 形态 | 默认值 | 是否可关闭 |
|------|--------|--------|--------|----------|
| 安全 | 影响在制工单 → 必须人工 | Locked Toggle | 开 | ✗ 不可关 |
| 安全 | 关键件 → 必须人工 | Locked Toggle | 开 | ✗ 不可关 |
| 安全 | 单一来源 → 必须人工 | Locked Toggle | 开 | ✗ 不可关 |
| 安全 | 财务合规事项 → 必须人工 | Locked Toggle | 开 | ✗ 不可关 |
| 业务 | 延期 ≤ N 天自动同意 | Toggle + Slider 0-7 | 开 / 2 | ✓ 可关 |
| 业务 | 供应商等级 A 自动同意 | Toggle | 关 | ✓ 可关 |
| 业务 | 客户重要性 ≥ KA 必须人工 | Toggle | 开 | ✓ 可关 |
| 效率 | 跟催次数上限 | Slider 1-5 | 3 | - |
| 效率 | 自动同意金额上限 | Number 输入 | ¥10000 | - |

### 6.3 冲突预警示例

```
⚠️ 冲突检查
当前配置：
- 业务层："延期 ≤ 2 天自动同意"已开启
- 筛选规则："是否关键件 = 是"已选中

🔒 安全层覆盖：
关键件订单即使延期 ≤ 2 天也会进入人工确认，
因为安全层 > 业务层。
```

**这一块是面试讲解时最重要的产品判断展示位**：

> 这一块是低代码平台真正难的地方。配置项越多，规则冲突越多。我设计的三层固定优先级——**安全 > 业务 > 效率**——是用"产品约束"代替"用户脑力"。
>
> ISV 业务顾问配置时不需要去推理"如果同时勾选 A 和 B 会发生什么"，因为安全层的硬规则永远赢。冲突预警实时展示哪条业务规则在哪个场景下被安全层覆盖——让隐式冲突可见，是低代码平台的核心交互能力。

## 7. 模块六：模型路由策略 ⭐ 鼎捷化的强呼应

### 7.1 配置项表

| 任务类型 | 推荐模型 | UI 形态 | 默认值 |
|---------|---------|---------|--------|
| 意图识别 | DeepSeek-V3 / Qwen-Plus | 下拉 | DeepSeek-V3 |
| 槽位提取 | DeepSeek-V3 / Qwen-Plus | 下拉 | DeepSeek-V3 |
| 风险判断 | GPT-4 / DeepSeek-R1 / Claude Sonnet | 下拉 | GPT-4 |
| 异常诊断 | GPT-4 / DeepSeek-R1 | 下拉 | DeepSeek-R1 |
| 话术生成 | Qwen-Max / 文心一言-4 | 下拉 | Qwen-Max |
| 敏感数据场景 | 私有化部署模型 | 下拉 | 私有化-Qwen |

### 7.2 路由策略

```
┌─────────────────────────────────────┐
│ 路由模式                              │
│   ○ 静态配置（按任务类型固定）        │
│   ● 动态路由（按 Token 数 + 复杂度）  │
│   ○ 成本优先（最便宜的能完成就用）   │
│   ○ 性能优先（最强模型）             │
├─────────────────────────────────────┤
│ 演进路线（产品规划，不一定要做）       │
│   v1: 静态配置 ✓                     │
│   v2: 动态触发（按复杂度切换）        │
│   v3: 自适应（基于历史 ROI）          │
└─────────────────────────────────────┘
```

**面试讲点**：

> 模型路由这一块呼应了鼎捷 Indepth AI 多模型集成的工程现状（DeepSeek、GPT、通义千问、豆包、文心一言）。我在 UI 上做了一个**演进路线**：v1 静态配置（按任务类型固定）、v2 动态路由（按复杂度切换）、v3 自适应（基于历史 ROI）。这不是要 Demo 都做出来，是表达**产品路线图思维**——平台 PM 必须有这种"现在做什么、未来做什么"的判断。

## 8. 模块七：知识检索配置（RAG 钩子）

### 8.1 配置项表

| 配置项 | UI 形态 | 默认值 |
|--------|--------|--------|
| 引用知识源 | Multi-select [供应商档案 / 历史合同 / 物料替代规则 / 行业基准] | [供应商档案, 历史合同] |
| 检索时机 | Multi-select [跟催话术生成 / 风险判断 / 异常诊断] | [话术生成, 风险判断] |
| 检索粒度 | 三态 [供应商级 / 物料级 / 订单级] | 物料级 |
| Top-K | Slider 1-20 | 5 |
| 相似度阈值 | Slider 0-1 | 0.7 |
| 检索失败兜底 | 下拉 [使用默认话术 / 转人工 / 跳过该步骤] | 使用默认话术 |

### 8.2 面试讲点

> RAG 这一块的产品判断是 **"检索失败兜底" 必须显式配置**。RAG 在工程上经常失败——向量库连接超时、相似度都低于阈值、知识源没有命中——平台必须让 ISV 显式决定失败时怎么办。把"失败"作为一等配置项，是企业级 Agent 区别于 Demo 的关键。

## 9. Code View（高代码视图）

切换到 Code View 时，整个中间配置区变成代码编辑器：

```typescript
// 同一个 Skill 用 SDK 表达
import { Skill, Tool, ModelRouter } from '@digiwin/indepth-ai-sdk';

export const PurchaseFollowUpSkill = new Skill({
  metadata: {
    name: '制造业采购交期跟催',
    industry: ['装备制造', '汽车零部件'],
    isvRoles: ['businessConsultant', 'developer'],
    version: '1.0.0',
  },
  
  triggers: [
    { type: 'schedule', cron: '0 8 * * *' },
    { type: 'manual' },
    { type: 'naturalLanguage' },
    { type: 'event', sources: ['mrp.plan.changed', 'workorder.inserted'] },
  ],
  
  filters: {
    time: { dueInDays: 7, excludeCompleted: true },
    supplier: { 
      replyStatus: ['notReplied'], 
      tier: ['A', 'B'],
      delayRateThreshold: 0.3,
    },
    material: {
      isCritical: 'any',  // 三态:'yes' | 'no' | 'any'
      isSingleSource: 'any',
      hasAlternative: 'any',
    },
    impact: {
      affectsWorkOrder: false,
      affectsMRP: false,
      affectsCustomerOrder: false,
    },
  },
  
  actions: [
    {
      type: 'sendSupplierReminder',
      channels: ['taskCard', 'enterpriseWechat'],
      templateId: 'standard-reminder-v2',
    },
    {
      type: 'createExceptionTask',
      escalateTo: 'purchase-manager',
      requireHumanConfirm: true,
    },
    {
      type: 'callSkill',  // 多智能体协同钩子
      targetSkill: 'completenessAlert',
      condition: '${result.hasShortage}',
```

## 12. 给 Claude Code 的实现指引

### 12.1 推荐组件库

- shadcn/ui 已经覆盖大部分需要的组件
- 关键组件清单：
  - `Slider`（用于到货前 N 天、跟催次数上限）
  - `Toggle / Switch`（用于各种开关）
  - `Select / MultiSelect`（用于通知渠道、模型选择）
  - `Tabs`（用于左侧模块导航）
  - `Card`（用于配置卡片）
  - `Tooltip`（用于配置项说明）
  - `Sheet`（用于模拟运行抽屉）
  - `Alert`（用于冲突预警）
- Code View 需要：`monaco-editor` 或 `react-code-editor`

### 12.2 状态管理

- 用 `zustand` 或 `jotai` 管理 Skill 配置状态
- 状态 schema 必须和 Code View 输出的 TS 接口完全对齐——这是双向可读的工程基础

### 12.3 冲突预警的实现

不要用复杂的规则引擎，用简单的 `useMemo` + 硬编码冲突规则：

```typescript
const conflicts = useMemo(() => {
  const result = [];
  
  // 规则 1: 关键件 + 业务层自动同意冲突
  if (filters.material.isCritical === 'yes' 
      && automationBoundary.business.autoApproveIfDelayLE > 0) {
    result.push({
      type: 'override',
      message: '关键件订单即使延期 ≤ N 天也会进入人工，因为安全层 > 业务层',
    });
  }
  
  // 规则 2: 影响在制工单 + 自动同意冲突
  // 规则 3: ...
  
  return result;
}, [filters, automationBoundary]);
```

### 12.4 视觉风格

- 主色调：蓝灰 `#3B5C7E` + 强调色 `#0EA5E9`
- 背景：浅灰 `#F8FAFC`
- 配置卡片：白底 + 极轻阴影
- 强调"工业级"质感——不用任何渐变色或玻璃拟态
- 字体：系统字体栈，B 端工具的标准做法
